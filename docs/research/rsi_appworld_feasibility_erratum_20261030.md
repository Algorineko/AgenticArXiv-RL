# AppWorld 受限接口可行性更正（2026-10-30）

此前两条参考解 2/2 通过，使用的是 trusted Python 执行和默认较宽 API 预算，不能证明“单次原生 API 的 JSON 代理＋48 次交互＋12/24 个模型响应”条件足以完成任务。

原私有参考日志分别包含 71、145 次原生请求。新增受限检查：在单次 trusted reference 执行内设置最多 48 次原生请求，两条参考解均在第 48 次达到上限并失败（0/2，执行 traceback）。公开摘要与私有日志 SHA256 见 `artifacts/rsi_appworld_reference_cap48_v1/`；没有发布解答源码或原生请求内容。

这不是同预算模型对照：trusted reference 已知道解答，不承担探索成本，且仍可执行 Python。它也不是最短解下界，不能说所有策略在 48 次内都必然失败。它揭示的是，原先用宽预算参考解为紧预算代理背书的证据不足。

据此暂停以这两个暴露场景的 0/2 推断模型或 RSI 的能力上限。先导失败仍真实保留，但其解释是“当前模型/接口/预算组合尚未通过健康基线门槛”。下一阶段在 meta_train 内核查参考策略请求量与工具表达能力，再冻结适合的接口/预算，并用多个训练场景标定约 20%–85% 的非饱和基线。不能读取最终集来挑容易题。

可选路径：扩充已计量的原生调用预算，或者采用官方程序式环境，但后者必须隔离任务解答与检查器访问，并使各方法共享相同表达能力。不能只给递归方法更强批处理接口，再把工具升级的收益写成递归收益。未经核查，不继续无限添加手工提示。
