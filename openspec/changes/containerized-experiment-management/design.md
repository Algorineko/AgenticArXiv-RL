# Design

## Context

动机与产品范围见 `proposal.md`，外部行为见本变更的两份 spec。本设计需要跨 CLI、容器启动、训练状态与研究产物边界，符合创建设计文档的条件。

- 已有 `agentic-arxiv` 轻量入口、独立安装层级、显式工作区、严格 JSON 训练配置、模型/数据 manifest 和单机 DDP 启动器；不应另建训练框架。
- SFT/DPO 当前调用 `trainer.train()`，GRPO 已传入恢复参数，但只验证路径存在。SFT/DPO 默认每 50 步保存，GRPO 默认不周期保存。既有恢复入口不等于完整恢复契约已经成立。
- DPO 明确拒绝覆盖已有输出；SFT/GRPO 会在输出目录写运行记录。`RolloutAuditWriter` 初始化会清空指定轨迹文件。恢复必须隔离尝试目录，不能直接重用旧输出路径。
- GRPO 的零方差保护、Canary 有内存累计状态；奖励课程依赖逻辑训练步数。固定版本 TRL 还持有微步计数和生成结果复用缓存，不能仅恢复全局步数就视为等价。依据：[TRL 0.29.1 源码](https://raw.githubusercontent.com/huggingface/trl/v0.29.1/trl/trainer/grpo_trainer.py)。
- 另一个聊天的历史检查记录显示：Ubuntu 22.04.5，4 张驱动识别为 RTX 4090 的 GPU，每卡约 48GB；已完成单卡 SFT 和四卡 SFT 冒烟。这不是当前空闲状态、Docker GPU 配置、完整恢复或新 DPO 训练已通过的证明。
- `ding` 使用独立数据目录，用户表示后续可以授予 docker 组权限。此前系统盘使用率较高，容器镜像和构建缓存也需由管理员核验存储位置；本变更不自动修改系统设置。

## Goals / Non-Goals

**Goals:**

- 管理层只决定执行对象、资源、目录和生命周期，训练层继续决定算法及研究语义。
- 将一次运行的不可变实验身份与可重试的执行尝试分离，提供明确的状态和证据链。
- 在固定版本、固定配置的受支持单机路径内实现真正的三阶段恢复，正常停止可恢复、强制停止不伪报保存成功。
- 容器工程回归、真实训练恢复和模型质量评测分别验收。

**Non-Goals:**

- 不将运行记录系统扩展为数据库服务或调度平台，不接管其他用户或手工启动的容器。
- 不实现跨机器/卡型/卡数恢复、变更学习率或延长预算的“等价续训”，不新增 QLoRA 分片或 vLLM 路径。
- 不原地升级旧产物，不接管当前仍在运行的旧后台训练，不用重新训练证明登记成功。
- 不把 checkpoint 权重恢复、推理重载、完整训练恢复和模型收益混为一种验收。

## Decisions

### 1. 服务端轻量控制端与容器训练端分离

在现有 CLI 中增加 `experiment` 命令族，业务放在独立的 `experiments` 模块，按配置、文件记录、容器操作和汇总职责组织，复用现有来源审计和训练入口。管理端使用基础安装层，不导入 torch/TRL；通过参数数组调用 Docker/Compose，不拼接可执行 shell 字符串，也不新增 Docker Python SDK 依赖。

训练镜像正常安装项目分发包与训练/日志依赖；单卡调用现有训练命令，多卡调用现有 DDP 启动器，一个容器内部运行所有 rank。容器不得挂载 Docker socket。新增运行控制参数由命令显式传入，不作为严格算法配置的新必填字段。

替代方案：不做独立 `trainctl` 命令族，避免双入口漂移；不把管理端塞进需要控制 Docker 的特权容器；不新增后台控制服务。

```text
[Server CLI] --> [Config + Run records] --> [Docker / Compose]
                                               |
                                               v
                                     [Existing training CLI]
                                               |
                                  +------------+------------+
                                  |            |            |
                                 SFT          DPO          GRPO
                                  |            |            |
                                  +------------+------------+
                                               |
                                    [Attempt-local outputs]
```

### 2. 固定镜像，分开管理构建与运行

采用与服务器已验证栈相容的 Python 3.10 / CUDA 12.6 Linux 镜像作为构建起点。基础镜像摘要、cu126 PyTorch 来源、完整依赖解析结果和项目 wheel 均在构建时固定；不能仅把当前几个顶层版本写成约束后宣称完整锁定。保留已验证栈，不借容器化升级 Transformers、TRL 或训练实现。

镜像构建、导入/拉取是明确的准备操作，`experiment start` 只运行已存在且摘要匹配的镜像。镜像中不复制模型、研究数据、输出目录、凭据或本地缓存；正式运行不挂载可变源码覆盖已安装代码。镜像记录代码提交、构建来源、Python/依赖版本和恢复协议版本；有未提交代码时不得把它伪称为某个干净提交。

Compose 是经过版本管理的资源/挂载模板，不是队列；每次保存最终渲染配置。使用非自动重启策略，不设置自动删除任务容器，避免退出证据和身份丢失。显式声明共享内存大小，不以特权模式或共享宿主机 IPC 掩盖配置问题。离线实验禁用意外模型下载，不向外发布端口。

GPU 容器仍依赖宿主机驱动和运行时，参见 [NVIDIA 官方安装说明](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)。管理员核查 Docker/containerd 存储位置和日志轮转；仅将模型目录移到数据盘不能解决镜像占用系统盘的问题，参见 [Docker 存储说明](https://docs.docker.com/engine/daemon/)。docker 组具有高权限，不能将它描述为普通无害权限，参见 [Docker 权限说明](https://docs.docker.com/engine/install/linux-postinstall/)。

### 3. 配置保持三层且可审计

管理配置使用带 `schema_version` 的 JSON，沿用仓库结构化读取和严格校验习惯，不引入额外配置语言或任意脚本执行字段。

| 层级 | 内容与优先级 |
|---|---|
| 服务器 profile | 工作区、运行根目录、允许输入根目录、缓存、镜像摘要、普通用户 UID/GID、GPU 可选范围及容器资源上限 |
| 实验 recipe | 实验组、阶段、训练配置来源、明确输入引用、评测配置、保存策略、预算口径 |
| 显式本次参数 | GPU 选择、随机种子、名称及允许覆盖的训练参数，优先于 recipe 并逐项记录差异 |

服务器配置不能覆盖算法值；路径映射先明确解析，再校验不存在歧义或输入/输出重叠。原训练配置仍由现有解析器校验，管理层不实现第二套算法默认值。

六份 recipe 是可填写真实输入的模板，不将示例路径、现有冒烟输出或未知 DPO 配方描述为可直接正式使用。受管配方显式设置周期 checkpoint：初始建议沿用 SFT/DPO 的 50 步、GRPO 采用 10 步，均可在新运行启动前修改并记录，不改原裸训练命令默认值；短程验证显式缩短周期。

M0 仅评测；M1 可训练或登记已存在的正式 SFT；M2 引用 SFT；M3/C1 引用同一 SFT；M4 引用明确 DPO 并追溯其 SFT。M3、M4、C1 的训练任务池和筛选政策必须记录，不能因起点不同偷偷重筛选后声称只有训练阶段变化。已有 DPO 数据生成、GRPO 探针/筛选继续显式使用原入口，不由管理命令补跑。

C1 的总步数在启动前确定，记录 M4 对照及偏好生成、DPO、后续 GRPO 的成本口径。管理器只校验和报告，不自动估算缺失成本、不运行预算搜索，也不把已完成 M3 延长预算当成 C1 的等价实现。

### 4. 文件记录取代数据库，运行和尝试分离

在用户指定的数据盘管理根目录保存以下逻辑结构，不改动原 `/data/ding/runs` 下的旧训练：

```text
experiment-root/
  profiles/
  recipes/
  registrations/<artifact-id>/reference.json
  runs/<run-id>/
    run.json
    resolved-config.json
    inputs.json
    attempts/<attempt-id>/
      attempt.json
      control/
      events.jsonl
      status.json
      logs/
      output/
        checkpoint-<step>/
        final/
    evaluations/<evaluation-id>/
```

`run.json` 固定实验身份和总预算；每次启动/恢复有新的 attempt，保存容器 ID、标签、源 checkpoint、生命周期和单独输出。`status.json` 是可核对的状态快照，不是唯一事实来源；原始事件、容器状态、训练结果和验证报告共同支持展示结论。

使用同文件系统原子替换、必要持久化和短期文件锁保护记录更新。活动运行和 GPU 声明持久化到记录，不能只依赖启动 CLI 进程持有的锁，因为 CLI 会立即退出。下一次命令调用核对原容器后才能释放旧声明；状态不明时保守拒绝争用，不自动清理。

恢复来源和旧尝试只读，新尝试写入新路径，解决 DPO 拒绝覆盖和轨迹日志清空问题。当前尝试的 checkpoint 轮转不跨尝试删除，首版不提供自动历史清理或磁盘回收任务。替代方案：不采用 SQLite 或后台监控进程，当前单机规模不需要额外服务和迁移成本。

### 5. 命令边界与单次操作

| 命令 | 行为 |
|---|---|
| `experiment check <recipe>` | 检查配置、环境、输入和资源，展示解析结果，不建立训练运行；必要的 tokenizer/协议审计在只读、无训练 GPU 的短生命周期校验容器中执行 |
| `experiment register <group> --model <path>` | 校验并只读登记已有最终产物，独立记录未知项，不产生训练或恢复资格 |
| `experiment start <recipe> --gpus <ids>` | 启动一个新运行；M0 对应单项评测，其余对应一个明确训练阶段 |
| `experiment list/status/logs` | 列出记录、核对当前状态、读取主进程或指定 rank 日志；不触发训练 |
| `experiment stop <run-id>` | 对活动尝试提交安全停止请求 |
| `experiment stop <run-id> --force` | 身份核验后显式强制终止活动尝试，不自动选择其他容器 |
| `experiment resume <run-id> --checkpoint <ref>` | 通过严格兼容性检查后建立新尝试，继续原预算 |
| `experiment evaluate <ref> --kind benchmark` | 手动执行统一正式评测，记录精确模型和评测配置；为默认评测种类 |
| `experiment evaluate <ref> --kind stage` | 仅重试已有最终产物的阶段验证，不重新训练，不覆盖旧报告 |

命令的具体参数帮助、退出码和 JSON 输出契约在实现中统一；成功创建后台尝试与训练最终成功是不同事件。命令不得包含隐含自动依赖执行、通配所有实验、自动换卡或自动重试。已有实验通过只读登记或精确输入引用使用，不能收编正在运行的外部进程。

### 6. GPU 与路径保护不冒充全局调度

使用 GPU UUID 固定宿主机设备身份和 rank 顺序，记录用户输入的设备编号及解析结果；容器内部使用其可见设备编号，不把宿主机编号原样当作容器本地编号。恢复保持同一 UUID 集合及顺序。容器 GPU 选择按 [Compose 官方接口](https://docs.docker.com/compose/how-tos/gpu-support/)配置。

启动先取得管理根目录的短锁，检查活动声明并保留本次启动意图，再检查外部 GPU 计算进程、重新确认选卡并启动容器。冲突直接失败；这只能保护本管理范围，外部用户仍可能在检查后启动任务，文档必须披露竞争窗口，不杀其他进程解决冲突。

输入按实际需要做最小只读挂载，旧 adapter/manifest 中的绝对路径在容器内保持同一路径，避免为容器迁移修改历史来源。当前尝试输出、控制目录和明确缓存可写。所有路径先规范化并检查允许根目录、符号链接及祖先/后代重叠。不得把整个用户主目录、SSH 密钥目录或全部数据盘直接可写挂进训练容器。

### 7. 生命周期以证据为准

启动先记录唯一 attempt 和确定性容器名称，再创建容器、记录其 ID、启动并返回。断线或命令异常后按名称、标签、UID、run/attempt ID 核对真实对象；不得因没有收到成功响应就重复启动。创建失败无容器时保存失败事件并释放声明；结果不确定时保留声明，等待明确查询。

展示三个独立维度：

- 执行：准备、启动中、运行中、停止处理中、已退出、未知。
- 训练：未开始、进行中、用户安全停止、预算完成、保护器提前停止、失败、强制中断。
- 验证：未执行、进行中、通过、失败、显式跳过、被中断；正式评测另有独立记录。

正常训练完成后沿用原阶段验证；用户安全停止只生成完整 checkpoint，不导出成功 final 或启动验证。失败/保护原因优先于并发用户请求，实际预算已经完成则记录自然完成。训练已完成但验证被中断时禁止继续增加训练步数，使用显式 `evaluate --kind stage` 重新验证。

阶段验证和正式评测中的停止不产生训练恢复点；在可取消的 episode 边界记录中断，不能返回部分结果冒充完整通过。后端未返回时保持停止处理中，只有显式强制操作才能终止。重新评测建立新记录，不提供评测内部断点恢复。

### 8. 完整 checkpoint 是事务化训练状态

训练端新增窄范围的保存/恢复适配，继续委托现有 Trainer 写标准模型、优化器、调度器和各 rank 随机状态，不改 loss、采样和训练算法。适配固定依赖版本，显式验证所需接口，版本不支持时在训练前失败，不静默降级。

checkpoint 附加一个版本化恢复清单，至少包括：阶段、run/attempt、逻辑步数、原总预算、rank/设备映射、模型/基座/冻结参考身份、输入及配置指纹、运行时/依赖身份、文件清单、附加状态版本和完成标记。保存精度状态时按实际启用情况记录，例如无 GradScaler 时明确不适用。

保存先进入同文件系统的未完成目录，所有 rank 完成自己的必要文件后协调确认；主进程核验清单并持久化，最后发布完成标记和最终目录。原训练器的 checkpoint 轮转必须推迟至完整提交之后。保存失败保留诊断，不污染上一个完整 checkpoint；磁盘不足也不能先删唯一有效恢复点。

恢复核对完整标记、必要文件哈希和每个 rank 状态，拒绝半写、损坏、仅权重或错误来源。模型加载只使用已登记、指纹匹配的自有训练产物；文件哈希只证明完整性，不将任意外部 checkpoint 变成可信输入。

### 9. 精确承接训练状态，不重新发放预算

首先重建与原运行相同的原始策略起点和冻结参考，然后只将恢复权重应用于可训练策略，恢复优化器、调度器、精度、数据/采样位置及各 rank 的 Python/NumPy/CPU/CUDA 随机状态。保持原总步数、epoch 和调度计划，恢复前后输出目录等操作字段可不同，研究字段必须一致。

受管配方可以预先声明优化步总预算，或声明原始 epoch 总预算。epoch 模式保持 `max_steps=-1` 和原 epoch 数，不在管理端依据原始行数猜算步数；由固定版本 Trainer 根据真实数据加载器与批量配置，在首次优化前核定各 rank 一致的 `state.max_steps`。当前尝试保存独立的预算核定记录，完整 checkpoint 绑定核定总步数及原 epoch 预算。恢复时保留原排程参数，并要求 Trainer 重新计算的总步数与已提交预算一致，不以剩余 epoch 另发预算。

DPO 的源数据仍绑定最初 SFT，而不是恢复 checkpoint；参考仍为独立冻结的完整原始 SFT。GRPO 保留最初 SFT 或 DPO 的参考身份。校验应覆盖参考权重不变及其不进入优化器，不能只比较目录路径。

GRPO 附加恢复内容包含：微步/生成窗口位置、仍需复用的生成缓存与相关旧策略信息、采样游标、奖励课程逻辑步数、零方差保护计数和标志、Canary 计数/结果及影响后续判定的状态。缓存按 rank 保存为可还原的结构与张量，不以重新采样替代。附加状态在任何后续 rollout/优化/保护回调前恢复；不能仅依赖通用 Trainer 的恢复就假定这些内存状态已保全。

旧停止请求属于原 attempt，不在新 attempt 自动再次生效；训练保护状态则必须承接。因保护终止或已耗尽预算的运行不开放普通 resume，修改研究设置属于新实验。

轨迹和指标输出始终写入新 attempt。checkpoint 前已提交的统计状态从断点恢复，原尝试在该点之后的失败/重算证据保留但不重复计入逻辑进度；使用 attempt、逻辑步数和样本/组标识区分。所有实际耗时仍计入成本，不因回滚而消失。

替代方案：不采用“加载 adapter 后重新 train”、改变 `max_steps`、清空保护器、丢弃生成缓存或缩减生成复用次数的近似恢复。

### 10. 安全停止采用显式请求协议，不调用默认超时终止

控制端原子写入带 attempt 身份的停止请求，重复请求幂等。训练端只在合适回调位置读取；DDP 在所有 rank 共享的优化步边界传播决定，不在各自工具交互轮次加入 collective。完成当前优化更新后保存完整状态，包括未消费生成缓存，再确认用户安全停止并退出。

默认停止不使用会超时自动杀进程的容器停止流程，不设“等待到期就强制”的隐含策略。当前模型生成、工具调用或通信没有返回时显示等待与最后进度；显式 `--force` 才终止核验过的目标容器。CUDA/NCCL 已故障时不为了保存再次发起不安全 collective，任务失败并保留最后完整恢复点。

训练自然完成、保护器触发和用户请求并发时，先记录实际故障/保护事实，再记录预算完成，只有尚有未完成预算且没有更高优先级原因才标记用户安全停止。保存失败不能返回“已安全停止”。

### 11. 成本与评测记录分开

首版提供文件化摘要和已有 TensorBoard 日志，不搭建看板服务或第三方实验平台。GPU 成本使用明确的分配卡数乘实际占用时长，标注为分配 GPU-hours 而非 FLOPs 或有效利用率；拆分启动、训练、保存、阶段验证、正式评测及失败重算成本。生成 token 数等指标沿用可信实际记录，缺失项标记未知。

预算比较引用明确运行和外部数据生成报告，记录来源与口径。共享 SFT 产物只训练一次，但每个实验分支的训练后成本单独列出；M4 的偏好生成与 DPO 成本不能因产物复用而在 C1 对照中消失。

正常完成阶段验证沿用现有阈值和协议；正式 benchmark 是独立手动任务，固定评测配置且不参与训练筛选。阶段验证被跳过或失败不能自动放行正式依赖链；若仅做诊断评测，记录诊断性质，不升级输入资格。

### 12. 分层验证与声明范围

工程检查覆盖基础安装隔离、CLI/JSON 配置、路径与身份保护、记录事务、状态协调、GPU 冲突、断点完整性和现有训练回归。复用已有测试替身与研究输入；可以构造控制元数据和临时目录，不新增合成论文、响应、token 序列、偏好或轨迹充当真实恢复证据。

真实恢复验证在另行授权后进行，先单卡，再四卡，对 SFT、DPO、GRPO 分别比较固定总预算的连续运行和中断恢复。两条对照从开始就使用相同总步数，不能先按短预算训练再延长 `max_steps`。覆盖安全停止、已有完整 checkpoint 后强制停止、损坏断点拒绝、原始参考不变、保护状态承接以及 GRPO 生成缓存消费位置。

逻辑步数、样本/组消费和保护计数要求一致；权重/logits 等按预先声明的容差比较并保留差异。比较中额外探针不能消耗一条路径的训练随机流，探针执行需隔离随机状态。默认 QLoRA 的单卡和四卡是首个实测目标；其他既有资源路径保持原入口兼容，但没有证据时不能扩张已验证范围。

偏好包、模型或快照缺失时不生成假的替代品；独立数据准备授权不包含在本次规划或未来默认工程实现中。工程完成与真实部署门禁分别列明；只有相应真实恢复检查通过，才宣称该阶段/资源组合的容器恢复已验证。

## Risks / Trade-offs

- [依赖私有恢复状态] 固定版本的 GRPO 有生成缓存和内部计数 → 通过窄版本适配、接口断言和真实恢复对照控制风险，不假定升级后仍兼容。
- [恢复状态和原始轨迹体积增加] 全量状态及多尝试证据占用磁盘 → 显式周期、当前尝试内轮转、可用空间预检和只读历史；首版不自动清理旧尝试。
- [安全停止等待较久] GRPO 多轮生成和跨 rank 协调可能耗时 → 展示停止处理中和最后进度，提供独立强制选项，不承诺固定响应时限。
- [共享服务器存在检查竞争窗口] 其他用户不遵守本管理记录 → 披露非全局调度边界，启动前复查，不终止外部任务。
- [系统盘被镜像或日志占满] 研究输出挂载到数据盘仍不足 → 部署前由管理员核验实际 Docker/containerd 存储和日志轮转；不擅自迁移或重启。
- [容器化不等于完全隔离] docker 组权限强、挂载可接触宿主机 → 普通容器用户、最小挂载、无 socket/特权、精确身份校验和共享服务器权限说明。
- [历史模型可用但历史 checkpoint 不完整] 旧产物没有新恢复元数据 → 只读登记为新实验输入，不升级旧记录或承诺旧训练可以完整续接。
- [GPU 计算非逐位确定] 完整状态相同仍可能出现浮点差异 → 记录容差与环境，严格区分数值误差和控制流/参考/数据消费错误。
- [未完成部署验证被误报可用] 本机工程测试无法证明四卡恢复 → 任务和报告独立列出真实验证状态，缺授权或资产时保留待执行状态。

## Migration Plan

1. 先实现和验证基础安装下的管理命令、配置及文件记录，不修改现有运行环境。
2. 构建独立固定镜像，保留原虚拟环境；生成可填写的服务器 profile 和六组 recipe，不将示例配置直接用于正式训练。
3. 补齐训练端完整 checkpoint、严格恢复、安全停止和尝试隔离，完成仓库内检查。
4. 用户另行授权部署后，由管理员/用户确认 Docker 权限、GPU 运行时、数据盘和镜像存储；不得自动修改全局服务。
5. 在空闲且明确授权的 GPU 上用已有合格输入完成单卡、四卡短程验证，产物写入全新验证目录，保持已有正式 SFT 和其他任务不变。
6. 通过门禁后只读登记已有正式模型，再由用户逐项启动实验；不迁移正在运行的旧任务。
7. 回退时停止新增受管任务并恢复使用原虚拟环境和旧入口；保留新旧产物、镜像与失败证据，不通过删记录或改写旧 manifest 完成回退。

## Open Questions

- 部署时实际采用的基础镜像摘要、完整依赖锁文件和 Docker/Compose 版本须在可访问的构建环境确定，不能填写未经核验的摘要。
- Docker GPU 支持、当前磁盘空间、运行时存储位置和可用 GPU 须在后续授权部署时重新检查，历史记录不能代替。
- 正式 DPO 偏好包、各 GRPO 训练任务池及 C1 具体预算须在运行前提供；这些是配方实例输入，不改变上述管理或恢复架构，缺失时预检拒绝正式运行。
